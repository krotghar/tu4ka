# nginx, TLS и бета-среда

Сессия I1 плана мульти-тучковой версии плюс вторая среда на том же VPS.
До неё uvicorn держал `0.0.0.0:80` напрямую, и второму приложению встать было
некуда — поэтому бета и nginx приехали одним куском.

## Что где слушает

```
           :80  ──┬─ default_server ──────────► 127.0.0.1:8000   (прод)
                  ├─ push.amqi.am ────────────► 127.0.0.1:8000   (прод)
   nginx          ├─ amqi.am / www ─── 301 ───► https
                  └─ beta.amqi.am ──── 301 ───► https
           :443 ──┬─ amqi.am / www (default) ─► 127.0.0.1:8000   (прод)
                  └─ beta.amqi.am ────────────► 127.0.0.1:8001   (бета)
```

Приложения наружу не слушают вообще: сокеты подняты на loopback.

## Среды

| | prod | beta |
|---|---|---|
| имя | `tu4ka` | `tu4ka-beta` |
| корень | `/opt/tu4ka` | `/opt/tu4ka-beta` |
| env | `/etc/tu4ka/env` | `/etc/tu4ka-beta/env` |
| БД | `/var/lib/tu4ka/tu4ka.db` | `/var/lib/tu4ka-beta/tu4ka.db` |
| юниты | `tu4ka.{service,socket}` | `tu4ka-beta.{service,socket}` |
| сокет | `127.0.0.1:8000` | `127.0.0.1:8001` |
| ветка | `main` | `dev` |

Всё выводится из `TU4KA_ENV` (`prod` по умолчанию) в `deploy/deploy.sh` и
`deploy/remote_setup.sh`. Прод-юнит намеренно **не переименован** в
`tu4ka@prod`: `systemctl status tu4ka` и `journalctl -u tu4ka` разбросаны по
документации, а дублирующийся файл юнита остаётся видимым в ревью, в отличие
от sed-рендера.

`remote_setup.sh` в шапке сверяет `TU4KA_ENV` с собственным путём и отказывается
работать при расхождении. Без этой страховки копия скрипта из
`/opt/tu4ka-beta/deploy/`, запущенная без переменной, считала бы себя продом и
переписала бы прод-юнит.

## Обновления без даунтайма

Слушающий сокет держит systemd (`ListenStream=127.0.0.1:8000`), а uvicorn
получает готовый дескриптор: `ExecStart=… uvicorn server.main:app --fd 3`.
При `systemctl restart tu4ka.service` порт **не закрывается** — соединения
копятся в очереди ядра и достаются новому процессу. Вместо секунды отказов
получается секунда ожидания.

Правило: на выкладке рестартовать **только `.service`**. Рестарт `.socket`
пересоздаёт дескриптор и возвращает дырку — делать это осознанно и только когда
менялся сам файл сокета.

Перед приложением nginx, который перезагружается изящно (`reload` поднимает
новых воркеров, старые дорабатывают открытые соединения), так что правки
конфига бесплатны.

Чего этим **не** починить: миграция схемы, перестраивающая `measurements`
целиком, — это блокировка записи в SQLite, а не рестарт процесса. Спасает
репетиция на бете, где та же миграция прогоняется на тех же данных.

Проверяется прямым экспериментом, не на веру:

```bash
fails=0; for i in $(seq 1 300); do
  curl -fsS -m 5 -o /dev/null https://beta.amqi.am/healthz || fails=$((fails+1))
  sleep 1
done; echo "отказов: $fails"        # ждём 0
```

## Путь датчика неприкосновенен

Датчик прошит на голый IP `http://178.160.230.131/api/v1/push`, basic auth, раз
в 60 с, **без буфера и ретраев**. Отсюда два жёстких инварианта в конфиге:

- на `:80` (и на голом IP, и на `push.amqi.am`) **нет редиректа на HTTPS**: при
  кросс-схемном редиректе теряется заголовок `Authorization`, а на 307 прошивка
  может не пойти вовсе;
- HSTS выдаётся **без** `includeSubDomains` — иначе браузеры начали бы
  требовать HTTPS и для `push.amqi.am`.

`client_max_body_size 128k` при `MAX_PUSH_BODY = 64 КБ` в `server/routes/push.py`:
413 остаётся ответом приложения, а не nginx, и в логах видно, что именно пришло.

## certbot

Только `--webroot`, никогда `--nginx`: деплой перезаписывает конфиг на каждом
прогоне, и правки плагина были бы молча затёрты.

Курица и яйцо (конфиг с `ssl_certificate` не даёт nginx стартовать, а HTTP-01
требует живого nginx) развязана так: **единственный файл, называющий
сертификат, не ставится, пока сертификата нет.** HTTP-фронт живёт сам по себе,
ACME-локация есть в каждом `:80`-блоке, включая редиректящие, — поэтому
продление работает всегда.

Выпуск загейчен наличием каталога lineage, так что certbot запускается ровно
один раз на имя за жизнь сервера; неудача не валит деплой, следующий прогон
повторит. Два отдельных lineage (`amqi.am` c SAN на www и `beta.amqi.am`):
общий сделал бы TLS прода заложником DNS беты.

Добавить новое имя в существующий сертификат гейт не даст — это делается руками
через `certbot certonly --expand`.

## Пересев БД беты

Датчик умеет слать только на один свой API, и он остаётся у прода. Поэтому на
каждом бета-деплое БД беты пересевается снимком прода:

- `VACUUM INTO`, а не `cp`: база в WAL, плоская копия без `-wal` невалидна;
- прод-база открывается **строго `file:…?mode=ro`** — root, открывший её на
  запись, создал бы `-wal`/`-shm` от root, и прод-сервис (юзер `tu4ka`)
  перестал бы писать;
- `sqlite3` берётся из stdlib питона в венве, новых пакетов не нужно;
- порядок: `stop` сервиса → снимок в `*.new` → снятие старых `-wal`/`-shm` →
  атомарный `mv` → `start`. Сокет при этом не трогается, так что запросы ждут.

Побочная польза: миграции схемы автоматически репетируются на боевых данных.

Направление одностороннее по конструкции: ничего не читает каталог беты и не
пишет в `/var/lib/tu4ka`.

## Переезд с :80 и откат

nginx не может занять `:80`, пока его держит uvicorn, — поэтому на самом
переезде было одно окно ~1–2 с между `restart tu4ka` и `start nginx`. Все
последующие деплои идут без окна вообще.

`remote_setup.sh` определяет переезд по наличию `--port 80` в живом юните,
сохраняет `tu4ka.service.prev` и при провале `/healthz` откатывается сам.
Гейт по факту переезда обязателен: без него обычный деплой с битым кодом тоже
останавливал бы nginx и выставлял сломанное приложение на `:80`.

Ручной откат:

```bash
ssh tu4ka systemctl stop nginx
ssh tu4ka 'systemctl stop tu4ka tu4ka.socket; cp /etc/systemd/system/tu4ka.service.prev /etc/systemd/system/tu4ka.service && systemctl daemon-reload && systemctl restart tu4ka'
curl -s http://178.160.230.131/healthz
```

## Почему не Docker

Обсуждалось и отброшено осознанно. `docker compose up -d` пересоздаёт контейнер
— порт секунду не слушает никто, ровно как `systemctl restart`; даунтайм он не
убирает, это делают socket activation и graceful reload nginx. Единственная
болячка, которую он вылечил бы, — незапиненные зависимости, и она закрыта
пином в `deploy/requirements.txt`. nginx и certbot всё равно остались бы на
хосте, так что контейнер накрыл бы только приложение и добавил слой между
отладкой и `journalctl`.

Решение обратимое: `server/` — нормальный пакет, состояние — один файл SQLite
вне кода.

## Проверки

```bash
ssh tu4ka nginx -t
ssh tu4ka 'ss -tlnp | grep -E ":(80|443|8000|8001)"'
ssh tu4ka 'systemctl status tu4ka.socket tu4ka-beta.socket --no-pager'

curl -sS -o /dev/null -w '%{http_code}\n' http://178.160.230.131/healthz   # 200, НЕ 301
curl -sS -o /dev/null -w '%{http_code}\n' http://push.amqi.am/healthz      # 200, НЕ 301
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' http://amqi.am/  # 301 https://…
curl -sSI https://beta.amqi.am/ | grep -i x-robots-tag                     # noindex, nofollow
```

Что бета читает бету, а не прод, проверяется дрейфом: сразу после пересева
`rows` в `/healthz` совпадают, через три минуты прод вырос, а бета — нет.
