# Домен и DNS

Домен проекта — **`amqi.am`**, куплен 2026-08-03, оплачен до 2027-08-03.
Регистратор — [name.am](https://name.am/account/domains/amqi.am/nameservers).

## Записи

Все три ведут на тот же VPS, что и раньше отвечал по голому IP
(см. [deploy-cicd](deploy-cicd.md)):

| Type | Name | Value | Proxy |
|------|------|-------|-------|
| A | `amqi.am` | `178.160.230.131` | DNS only |
| A | `www.amqi.am` | `178.160.230.131` | DNS only |
| A | `push.amqi.am` | `178.160.230.131` | DNS only |
| A | `beta.amqi.am` | `178.160.230.131` | DNS only |

Имена разведены по `server_name` в nginx (сессия I1): `amqi.am`/`www` — сайт,
`push.amqi.am` — приём, `beta.amqi.am` — бета-среда. См.
[nginx-tls-beta](nginx-tls-beta.md).

`push.amqi.am` остаётся заготовкой на случай переезда ingest на другую машину:
датчик по-прежнему шлёт на голый IP, прошивку не трогали.

## Зона живёт в Cloudflare, но это не наш аккаунт Cloudflare

В панели name.am есть переключатель **Nameserver | DNS Records**. Включён режим
`DNS Records` — и это встроенная интеграция name.am с Cloudflare: делегирование
уходит на `tori.ns.cloudflare.com` / `dave.ns.cloudflare.com`, менять nameservers
руками не пришлось.

Важное следствие: зона лежит **внутри аккаунта name.am**, а не в собственном
аккаунте Cloudflare. Тумблер проксирования на каждой записи есть, а вот cache
rules, WAF и API-токен — нет. Токен понадобится, если certbot придётся переводить
на challenge DNS-01; значит, «включить оранжевое облако» это не один клик, а
«завести свой аккаунт CF и перенести NS туда». Оценивать соответственно.

## Почему проксирование выключено

Оранжевое облако Cloudflare звучит как бесплатный апгрейд, но конфликтует
с обеими половинами инфраструктурного плана:

- **Ломает Let's Encrypt по HTTP-01.** Проверка владения доменом идёт запросом
  по HTTP на сервер; из-под прокси запрос до сервера не доходит, отвечает
  Cloudflare. Лечится DNS-01 или CF Origin Certificate — но см. выше про
  отсутствие API-токена.
- **Толкает в режим Flexible.** Это когда браузер↔CF шифруется, а CF↔сервер идёт
  открытым текстом. Замочек в браузере есть, сквозного шифрования нет. Массовая
  ошибка, и она хуже честного Let's Encrypt на самом сервере.
- **Не должно стоять на пути push.** Прошивка airRohr не буферизует и не
  ретраит: любая минута недоступности — безвозвратная дыра в истории. Лишний
  сетевой слой на этом пути — чистый риск без выгоды.

Взамен теряем немного: щит от DDoS (проблемы нет), CDN-кэш (дашборд — один HTML
плюс вендоренные шрифты), сокрытие IP (наполовину фиктивное — датчик всё равно
ходит на IP напрямую, порт 80 открыт миру). Решение обратимое: понадобится щит —
включается позже, вместе с переездом certbot на DNS-01.

## Имена разошлись с планом

План мульти-тучковой версии предполагал `tu4ka.<домен>` и `push.tu4ka.<домен>` —
домен тогда мыслился общим, не проектным. Раз `amqi.am` куплен специально под
тучку, префикс `tu4ka.` отброшен: сайт на голом `amqi.am`, приём на
`push.amqi.am`. Замысел плана — держать ingest на отдельном имени, чтобы его
можно было увести на другую машину, не трогая сайт, — сохранён.

## Проверки

```bash
dig +short A amqi.am @1.1.1.1                     # ждём 178.160.230.131
dig +trace amqi.am | tail -5                      # авторитетные NS — Cloudflare
curl -s http://amqi.am/healthz                    # {"ok":true,…}
```

Локальный резолвер может какое-то время отдавать `164.90.221.98` — это
парковочная страница name.am, залипшая в кэше до заведения записей. TTL 300,
проходит само; `+trace` и `@8.8.8.8` показывают правду сразу.

## Сессия I1 закрыта

nginx впереди, приложения на loopback (`8000` прод, `8001` бета),
`CAP_NET_BIND_SERVICE` из юнита убран, Let's Encrypt на `amqi.am`/`www` и
отдельно на `beta.amqi.am`; `push.amqi.am` и голый IP — HTTP:80 **без**
редиректа на HTTPS. Подробности и обоснования —
[nginx-tls-beta](nginx-tls-beta.md), формат приёма —
[protocol-airrohr-push](protocol-airrohr-push.md).
