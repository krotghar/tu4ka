# Схема БД и миграции

Как версионируется схема SQLite, почему именно так и обо что здесь легко
споткнуться. Раскладка модулей — [server-package-layout](server-package-layout.md),
среды и деплой — [nginx-tls-beta](nginx-tls-beta.md).

## Что было до

Схема лежала строкой `SCHEMA` в `server/db.py` и применялась `db.init_schema()`
из `lifespan` на каждом старте. Пока таблица одна и меняется она только вперёд
(`CREATE TABLE IF NOT EXISTS`), этого хватало. Как только понадобилось
перестроить `measurements`, схема перестала быть «создать, если нет» — стала
последовательностью необратимых шагов, которые обязаны применяться
по одному разу и по порядку.

## Устройство

- `server/migrations.py` — список `MIGRATIONS = ((версия, шаг), …)`. Шаг это
  либо кортеж SQL-инструкций, либо функция `apply(conn)`.
- `server/migrate.py` — раннер: `run()` применяет недостающее, `assert_current()`
  сверяет версию, `python -m server.migrate` — точка входа для юнитов и рук.
- Версия — в `PRAGMA user_version` (целое в заголовке базы; пишется
  транзакционно, отдельной таблицы под учёт не нужно).

Alembic не берётся сознательно: это инструмент экосистемы SQLAlchemy, его
autogenerate тут не работает, а всё нужное — «применить недостающие шаги
по порядку, каждый своей транзакцией» — умещается в один небольшой файл.

## Четыре решения, которые легко «упростить» обратно

**v1 равна старой схеме дословно.** Боевая база с `user_version = 0`
структурно уже находится на v1, поэтому применение v1 к ней ничего не меняет
(все `CREATE` — `IF NOT EXISTS`). Чистая и боевая базы сходятся в одной точке,
и ветка «а это legacy-база или новая?» не нужна вообще. Соблазн «начать
нумерацию с настоящих изменений» этот сход ломает.

**`executescript()` не использовать.** Он делает COMMIT перед запуском —
то есть разрывает транзакцию миграции ровно посередине. Отсюда и форма шага:
кортеж инструкций, которые раннер выполняет по одной через `conn.execute()`.

**Транзакция на версию, включая запись `user_version`.** Соединение
открывается с `isolation_level=None` (иначе явный `BEGIN` упрётся в неявную
транзакцию драйвера), DDL в SQLite транзакционен, `user_version` пишется
вместе с ним. Итог: упавшая миграция откатывается целиком и версию не двигает
— повторный запуск начнёт её с начала, а не с середины.

**Мигрирует отдельный процесс, а не приложение.** `ExecStartPre=python -m
server.migrate` в обоих юнитах. Перестроение таблицы не должно идти под живым
трафиком, а `lifespan` — это уже поднятое приложение. Само приложение только
сверяет версию (`migrate.assert_current()`) и **отказывается стартовать**, если
база отстала или, наоборот, новее кода: молча обслуживать запросы по чужой
схеме хуже, чем не подняться. Локально это значит, что после `git pull`
на свежей базе нужно один раз позвать `python -m server.migrate` — команда есть
в блоке команд `CLAUDE.md`.

## Порядок перестроения таблицы

Наивная последовательность «создать `measurements_new` → скопировать → дропнуть
старую → переименовать новую» здесь ломается: `ALTER TABLE … RENAME` в SQLite
разбирает все объекты схемы, спотыкается о внешний ключ `measurements_raw`,
указывающий на только что удалённую таблицу, и падает. Поэтому v2 идёт иначе:

1. `ALTER TABLE measurements RENAME TO measurements_v1` — на неё ещё никто
   не ссылается;
2. `CREATE TABLE measurements(…)` сразу под финальным именем;
3. перелить измерения (с `device_id = 1`, сохранив `id`);
4. `CREATE TABLE measurements_raw(… REFERENCES measurements(id) …)` — цель ссылки
   уже существует;
5. перелить `raw` из `measurements_v1`;
6. `DROP TABLE measurements_v1` — на неё снова никто не ссылается;
7. пересоздать `idx_measurements_ts` (он умер вместе со старой таблицей) и
   создать `UNIQUE INDEX idx_meas_dev_ts(device_id, ts)`.

Ни в один момент нет ссылки на отсутствующую таблицу, и переименовывать
готовую таблицу не приходится. `PRAGMA foreign_keys=off` раннер ставит явно:
в `sqlite3` проверка ключей и так выключена по умолчанию, но цена этого
умолчания слишком велика, чтобы на него полагаться.

## Уникальный индекс — не косметика

`UNIQUE(device_id, ts)` означает, что дубли по секунде в истории **уронят
миграцию целиком**. Это и есть желаемое поведение: выбирать, какое из двух
измерений на одну секунду лишнее, миграция не вправе. На боевой базе дублей
нет — проверено на снимке 2026-08-04, 0 из 14 899 строк. Проверка перед
следующим таким шагом:

```sql
SELECT ts, COUNT(*) c FROM measurements GROUP BY ts HAVING c > 1 LIMIT 20;
```

Обратная сторона того же индекса: приём должен пережить повторный пуш с той же
меткой времени. `server/routes/push.py` пишет через
`ON CONFLICT(device_id, ts) DO UPDATE` — прошивка не буферизует и не
переспрашивает, так что 500 в ответ означал бы безвозвратно потерянное
измерение.

## Что даёт вынос `raw`

Не место на диске: строки никуда не делись, файл после `VACUUM` похудел всего
на 0.1 МБ. Даёт он другое — горячая таблица перестала таскать за собой JSON.
Замер на снимке прода после миграции:

| таблица | размер |
|---|---|
| `measurements` | 1.0 МБ |
| `measurements_raw` | 10.6 МБ |

То есть любой скан по измерениям (а это `/history`, NowCast, профиль суток)
читает ~1/12 прежнего объёма. Сам `raw` не удаляется — это страховка для
будущих миграций; срок его жизни ограничит ретеншен в S5.

## Схема v2

```
devices(id, slug UNIQUE, name, chip_id, chip_id_conflict_at,
        push_user, push_secret_sha256,
        push_secret_prev_sha256, push_secret_prev_until, created_at)

measurements(id, device_id → devices.id, ts, sensor_id,
             pm10, pm25, temperature, humidity, pressure, signal)

measurements_raw(measurement_id → measurements.id, raw)
```

Заводятся ровно те таблицы, которые нужны сейчас. `users`, `sessions`,
`device_membership`, `device_latest`, `measurements_hourly` из целевой схемы
плана волн придут своими миграциями в тех сессиях, которые их пишут: схема,
спроектированная за три месяца до кода, почти наверняка потребует второй
миграции на исправление, а добавить таблицу раннером стоит десяток строк.

Про поля:

- `chip_id` — `esp8266id` прошивки, справочно. Для маршрутизации push
  не используется **никогда**: человек мог перепаять плату. Расхождение
  не отклоняется, а помечается `chip_id_conflict_at` — см.
  [per-device-push](per-device-push.md).
- `push_secret_prev_sha256` / `push_secret_prev_until` — grace-период при
  ротации токена. Без него перенастройка датчика означала бы дыру в данных.
- `sensor_id` остался в `measurements` построчно: его показывает дашборд
  («airRohr 2998975»), на нём висят тесты приёма. Дублирование с
  `devices.chip_id` осознанное и разрешится в сессии по мультидевайсному API.

Устройство 1 заводит сама миграция: `slug='tu4ka'`, `push_user` и SHA-256
от текущего `TU4KA_PUSH_PASS` из окружения, `chip_id` — тот `sensor_id`, что
прислал больше всего измерений. Креды читаются из окружения, а не из
`server.auth`: миграция обязана быть самодостаточной и не зависеть от того,
что успел прочитать в свои глобалы соседний модуль на импорте. Пустой пароль
(тесты, свежая машина) — норма, кладём `NULL`.

## Схема v3

Одна строка: `CREATE UNIQUE INDEX idx_devices_push_user ON devices(push_user)`.

В v2 уникален только `slug`, а `push_user` — обычная колонка. С переходом
приёма на креды устройства ([per-device-push](per-device-push.md)) по нему
выбирается устройство, и две строки с одним логином сделали бы выбор
недетерминированным: `LIMIT 1` без `ORDER BY` — это «какая попадётся».
Уникальность закрыта схемой, а не соглашением, потому что нарушить соглашение
сможет любая будущая форма заведения устройства.

Отдельными версиями придут `device_latest` (карта), `measurements_hourly`
и ретеншен, `users`/`sessions`/`device_membership` (аккаунты) — каждая вместе
с кодом, который её пишет.

## Репетиция на боевых данных

Пересев беты и есть репетиция, причём бесплатная: база беты переливается
снимком прода на каждом бета-деплое, `VACUUM INTO` сохраняет `user_version`,
значит `ExecStartPre` каждый раз прогоняет всю цепочку с нуля на данных
прод-формы. Сломанная миграция краснеет на бете, а не на проде.

Разовая проверка v2 на снимке `tu4ka-20260804-1908` (14 899 строк), 2026-08-04:

- `user_version = 2`, `integrity_check ok`, `foreign_key_check` пуст;
- 14 899 строк в `measurements` и столько же в `measurements_raw`, сирот и
  пропусков ноль, `MIN/MAX(ts)` совпали со снимком;
- `devices` → `(1, 'tu4ka', 'тучка', '2998975', …)`, хеш секрета сошёлся;
- повторный прогон — `схема уже на версии 2`;
- **сверка с продом**: `/api/v1/history?period=7d` — 56 корзин из 57 совпали
  байт в байт; разошлась ровно текущая, ещё наполняющаяся (`n=128` у прода
  против `n=107` в снимке — измерения, пришедшие после копии);
- дашборд на этой базе рисуется целиком, ошибок в консоли нет.

Прогон v3 на том же снимке, 2026-08-05: `применены миграции: 1, 2, 3`,
`user_version = 3`, `integrity_check ok`, 14 899 строк в обеих таблицах,
три индекса на месте. На этой же базе поднят сервер: push без кредов → 401
(в `devices` есть хеш), push с кредами → 200 и `pressure` 1008.5 гПа,
`/history` и `/hours` отвечают как раньше.
